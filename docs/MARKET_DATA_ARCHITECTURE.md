# SeeAlpha 统一行情数据架构（设计决策）

> 2026-11-20 确认。**这是未来重构必须遵守的架构目标，不表示代码已全部完成，也不授权生产部署。** 目录结构已按领域完成第一阶段迁移；行情持续维护能力仍在分阶段收敛，不代表完成验收或授权部署。

## 一句话目标

**用户配置要维护什么数据，系统就自主采集、计算、检查和修复；回测、策略、交易只是使用者，绝不能因为开始或停止使用行情而改变采集配置。**

例如，用户配置“Binance ETHUSDT 永续，自 2025-01-01 起维护历史数据，并保持实时采集”。即使没有任何回测或策略在运行，行情系统仍需按照这项配置持续维护 ETHUSDT。用户停止策略，不应停掉采集。配置关闭实时采集时，策略的读数据请求也不应偷偷重新启动采集。

## 数据源模块化原则（2026-11-20 补充）

数据生产端以 **交易所 × 市场类型** 为独立所有权边界，例如 Binance USD-M 永续、Binance 现货和 Binance 期权。每个模块可以独立维护、测试和按需部署；不要求每个模块立即拆成微服务或独立仓库。

- **协议与数据维护分离**：`engine/connectors/` 持有交易所协议和 Nautilus 适配；`engine/market_data/sources/<venue>/<product>/` 持有该市场的采集入口、专有校验和后续逐步迁入的维护规则。连接器不能反向导入数据源、访问层或交易策略。
- **三项可恢复任务**：实时采集、自动计算、历史扫描/核验/补齐可以独立失败和恢复；是否必须分别运行在三个 OS 进程由实际隔离要求决定。交易所不提供可核验历史来源时应明确记录不可修复状态，不能合成真实 Tick、期权双边报价或 L2。
- **通用能力只实现一次**：标准聚合、任务调度、Catalog/SQLite/Parquet 持久化适配、数据质量与统一只读访问仍属于公共 `market_data` 层；市场模块可提供专有实现，但不复制通用算法和存储体系。
- **配置驱动，不由消费者驱动**：仅授权的持久化行情配置决定生产任务生命周期。新增策略、回测、研究消费者不得改动采集配置，也不能直接依赖市场专有内部实现。
- **隔离与兼容**：新来源应不修改 Engine 核心、HTTP v2 契约、已持久化数据路径、租户授权及订单安全语义；并发写入仍遵守现有锁、幂等、检查点与质量门禁。市场模块失败不得隐式扩大到别的市场。
- **可验证的插件边界**：添加新交易所/产品应以新模块与明确注册/路由为主，而非在核心散布交易所分支；对每个模块分别验证配置、连通性、断线恢复、重启、历史缺口、数据质量和回滚。

### 本次 Binance 数据源实现迁移

- `sources/binance/perpetual/`：独立采集、计算、历史核验/补齐入口，以及 USD-M 专有资金费率采集与历史观测。
- `sources/binance/spot/`：独立采集、计算、历史核验/补齐入口。
- `sources/binance/options/`：期权实时采集实现与历史报价、成交、盘口证据维护实现。
- `sources/binance/shared/`：市场间复用的共享 WebSocket 批处理、逐笔持久化、计算和历史修复算法；它不负责决定某市场是否启动。各产品入口验证产品身份，复用公共核心以免复制错误敏感的处理逻辑。
- 旧 `collection/{futures_service,pair_service,options_service,funding_service}.py`、`calculation/pair_calculation.py` 和 `repair/{pair_data,options_data,funding_data}.py` 仍作为兼容导入。旧 `python -m engine.market_data.repair.pair_data` CLI 保留并委托新实现。
- 当前改动是**源码归属与调用入口迁移**；不是交易所网络行为重写、独立容器部署或生产运行验收。对现有存储目录、质量门禁、锁及 HTTP 契约不做更改。共享实现仍含少量产品分支，未来扩展新的 venue 时优先通过显式 source 路由而非复制核心。


## 1. 两个独立业务模块

### A. 行情数据管理（数据生产与维护）

**唯一的采集控制依据是授权的行情配置（DataPolicy / 其未来等价物）。**

- 用户原则上只需选择交易所/产品/交易对及历史起始日期；实时采集、历史维护和数据类型采用明确默认值或可选配置。
- 管理服务根据配置启动、关闭或调整数据任务，持续维护已配置的数据集。
- “是否有人正在看、是否有回测、是否有策略订阅”**不是**判断采集任务是否运行的依据。
- 配置明确关闭实时采集时，不得因为策略开始订阅就临时覆盖为开启；历史维护与实时采集的启停分别由配置决定。
- 配置只允许经授权的管理接口修改，记录修改来源与时间。未来若允许策略自动管理采集，应通过受控的配置接口显式修改配置，接受权限校验、审计和用户配置优先级约束；**策略的数据订阅接口仍然是只读需求声明**。

### B. 统一行情数据访问（数据消费）

- 回测、策略运行、交易中的市场估值/风控和研究查询使用统一的数据访问契约。
- 访问层按请求交付历史或实时数据、预热窗口与质量标记；可共享数据缓存，避免消费者重复读取相同内容。
- 同一市场数据可以被多个消费者读取；消费者取消订阅只释放自己的读侧资源，不影响采集配置与历史数据。
- 数据未配置、未采集、缺失或质量不符合请求要求时，明确报告不可用；**访问请求不隐式启动采集、修改配置或绕过修复流程**。
- 历史回测使用独立时间轴与回放作用域；实时策略使用实时会话与新鲜度检查，不混用缓存，不读取未来事件。
- 账户余额、实际持仓、订单和成交回报属于账户/交易执行事实，不属于公开行情管理；交易许可仍由风险/执行层独立判定。

简化关系：

```text
用户或有权限的配置管理接口
          |
          v
    行情配置（唯一控制依据）
          |
          v
    自动行情数据管理系统
       |       |       |
       v       v       v
   实时获取  自动计算  自动扫描/补齐
       \       |       /
        \      v      /
       已保存、已核验的数据
                |
                v
       统一行情数据访问服务
          |     |      |
          v     v      v
         回测  策略  交易/风控
```

**箭头只表示数据使用依赖，不表示下方消费者能直接控制上方采集任务。**

## 2. 延续永续合约的三个可独立恢复的程序

各数据产品尽量沿用现有永续合约的成熟分工，具体交易所协议可以不同：

| 程序 | 自己负责 | 自动恢复要求 |
| --- | --- | --- |
| 实时获取 | 根据配置连接 WebSocket/必要 REST，接收并保存来源数据 | 断线重连、检查连接交接、继续写入，不能静默丢弃 |
| 自动计算 | 根据真实来源生成和更新 1s/K 线等衍生数据 | 来源变化或历史补齐后重新计算受影响窗口，断点可续 |
| 自动扫描、核验、补齐 | 从配置起始日期持续审查覆盖与质量，发现缺失后从可信来源修复 | 定期重试、遵守来源发布时间与限流、保留无法修复的缺口 |

三项工作必须能独立失败、重启和继续，不要求用户日常手动追踪任务。这里说的**“无状态”是管理程序无需人工维持操作状态、能够从配置和持久化事实恢复**，而不是删除 SQLite、原始来源、缺口、检查点、水位、锁或质量记录。

任务应尽可能幂等；重启后的目标仍由配置计算。不可因为进程重启、订阅者退出、接口调用重试而清空或重建历史。存储不可用、数据冲突或来源无法验证时，保持明确的失败状态，不假装已修复。

## 3. 准确性是持续维护的目标，不是无条件承诺

- 永续合约现有“来源归档延迟后自动核验/补齐”的做法可作为其他产品的参照。用户期望约两天后数据趋于可用且准确，但这**不是对所有数据源的 48 小时完整性保证**。
- 原始成交、闭合 K 线、资金费率实际结算、期权报价和 L2 盘口各自有不同的权威来源、保存范围与可回补能力；不得把预估费率当作结算、把 K 线当成真实报价、把盘口快照冒充完整订单簿历史。
- 交易所不提供的历史 Tick、期权双边报价或盘口变动，不得合成后宣称真实、完整。
- 每条数据应可表达覆盖范围、来源、更新时间、是否闭合、是否经过核验、缺口或冲突、修复中/无法修复等信息。质量不足时，回测与实盘应按各自安全规则拒绝使用。
- 数据质量的 READY 不等于账户对账完成，更不等于允许新建交易风险。

## 5. 建议的重构次序（后续实施，不属于本次提交）

1. **固定配置优先级（已实施本阶段核心变更）。** 持久化配置唯一决定采集启停，移除消费者需求的隐式覆盖；后续持续核查其他配置入口。
2. **统一三项自动维护任务的组织方式。** 让永续、现货、期权等使用同一类任务协调规则，保留不同的连接器、计算器、可信历史来源和写入锁。
3. **统一读数据入口（已实施历史读取第一步）。** 历史回测经统一的只读 Catalog 适配器；实时策略通过现有 Journal Bridge 与共享市场数据服务读取；后续把交易估值等剩余直接连接器读取逐步迁移，同时保留独立回放时钟、租户权限与交易风险边界。
4. **统一质量与可观察性。** 可查询覆盖、缺口、修复进度、来源冲突、数据新鲜度；没有可修复来源时长期保留明确状态，而不是无限假重试。
5. **分阶段验收与切换。** 先离线/隔离租户，再真实行情长时运行；不修改真实账户和生产状态卷，不隐式切换 Platform/Engine 契约。

## 6. 必须满足的验收场景

- **配置开启，零策略：** 实时采集、自动计算与历史修复照常运行。
- **配置关闭，策略订阅：** 只允许读取既有且授权的数据；实时不可用时明确失败，不能偷偷启动 WebSocket。
- **最后一个策略退出：** 采集程序按原配置继续运行；只释放读侧资源。
- **新增交易对和起始日期：** 仅修改配置，三个程序自主开始工作；不要求人工逐项创建任务。
- **三个程序分别重启或断线：** 从持久化事实续做、检查未完成工作，不重复计算/丢失已确认的数据。
- **出现历史缺口：** 自动检测、根据官方可用来源补齐并更新受影响的衍生数据；不可补的缺口明确标记。
- **重复消费者读同一行情：** 尽量共享已保存的数据和读侧缓存，且每个消费者只能访问授权范围。
- **回测/策略只使用行情：** 不修改采集配置、不创建另一套历史采集或交易所连接；严格隔离回测与实时环境。

## 7. 非目标与安全边界

本设计不要求三个维护任务合并为单进程，也不要求新建远程微服务；先使用 Engine 内部清晰的模块边界。市场公共数据在各 Engine/租户之间是否跨实例共享属于**另一个需要安全评审的问题**，不能因此取消现有租户隔离和读写锁。

本次代码阶段仅变更采集控制与历史读取路径，不修改行情维护核心、数据库、已有配置或 HTTP 契约；不会启动采集或真实交易。按项目安排，长时间运行与完整验收延后，后续仍必须完成测试和正式部署评审。
